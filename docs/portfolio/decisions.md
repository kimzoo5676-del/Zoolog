# 기술적 결정 기록

무엇을 고를 때 어떤 선택지를 비교했고 왜 골랐는지, 결과가 어땠는지의 기록. 면접의 "왜 그 기술을 썼나요?" 질문 대비

형식: 상황 → 선택지 → 결정과 이유 → 결과 · 한계

---

## 1. 운영 서버: 노트북 셀프 호스팅 → AWS Lightsail (2026-10-12)

- **상황:** 처음에는 개인 노트북 + Tailscale Funnel로 공개할 계획. 노트북이 꺼지면 사이트와 매일 06:00 일정 메일이 멈추는 문제, 노트북 반납 예정
- **선택지:** 노트북 유지 / EC2 / Lightsail
- **결정:** Lightsail 서울 $12(2GB, 2 vCPU, SSD 60GB) + 고정 IP
- **이유:** 월 고정 요금(트래픽 3TB 포함)이라 비용 예측이 쉬움, 1인 비상업 서비스 규모에 충분, 콘솔이 단순
- **한계:** 버스트형 CPU라 서버에서 빌드하지 않음(빌드는 GitHub Actions), 메모리 2GB가 빠듯함

## 2. 배포 방식: Docker Compose → k3s + Argo CD (GitOps) (2026-10-12)

- **상황:** 처음에는 서버에서 Docker Compose로 실행할 계획. 클라우드 엔지니어 직무 준비로 쿠버네티스와 GitOps를 실제 운영해 보고 싶었음
- **선택지:** Docker Compose + SSH 배포 / k3s + kubectl 직접 적용 / k3s + Argo CD
- **결정:** k3s 1대 + Argo CD core
- **이유:**
  - Git이 운영 상태의 기준(단일 진실 공급원): 서버에서 손으로 바꾼 것은 Argo CD selfHeal이 Git대로 되돌림
  - 되돌리기가 `git revert` 한 번
  - k3s는 쿠버네티스 인증 배포판이라 같은 YAML이 EKS 등에서도 동작, 바이너리 하나로 메모리 사용이 적음
  - Argo CD는 웹 화면 없는 core 설치로 메모리 절약
- **결과:** 2GB 서버에서 k3s + Argo CD + 앱 4개가 동작(스왑 2GB 보조). 메모리는 관찰 중
- **비밀값:** Git에 넣지 않고 서버에서 k8s Secret으로 한 번 생성(Sealed Secrets 등은 규모 대비 과함)

## 3. HTTPS · 화면 제공: Caddy (2026-10-12)

- **선택지:** Spring이 React 빌드를 함께 제공 / Nginx + certbot / Caddy / k3s 기본 Traefik
- **결정:** Caddy가 HTTPS 인증서 자동 발급·갱신 + 화면 파일 제공, `/api`·로그인 경로만 Spring으로
- **이유:** 설정 파일 20줄 정도로 인증서 자동화, 정적 파일은 Spring을 거치지 않아 백엔드 부담 감소, 빌드 파일 1년 캐시
- **같이 바꾼 것:** Spring `forward-headers-strategy: native`(Caddy가 보낸 X-Forwarded-Proto로 https 인식, 없으면 Google 로그인 콜백 주소가 http로 만들어짐)

## 4. 무중단 배포: 화면 서버만 먼저 (2026-10-13)

- **상황:** 처음에는 메모리 때문에 모두 Recreate(옛 파드를 먼저 내리고 새 파드 시작, 배포 중 중단)
- **결정:** web(Caddy)만 RollingUpdate(maxSurge 1, maxUnavailable 0) + readinessProbe + preStop 5초 + Caddy grace_period 10초. 백엔드는 Recreate 유지
- **이유:** Caddy는 메모리 상한 128Mi라 배포 순간 2개가 떠도 부담 적음. 백엔드는 640Mi가 추가로 필요해 2GB 서버에서 메모리 부족 위험
- **결과 (측정):** 배포 중 1초 간격 요청에서 화면 응답 실패 0회(새 버전으로 바뀐 것을 ETag로 확인), API는 약 30초 502
- **다음 판단 기준:** 며칠 메모리 사용량을 보고 백엔드 RollingUpdate 또는 4GB 플랜 결정. 백엔드 무중단 시 고려할 것: Actuator readiness, 세션(파드 메모리 → 교체 시 재로그인, 여러 개면 Spring Session JDBC), 옛·새 버전 동시 실행에 맞춘 하위 호환 마이그레이션

## 5. 로그인: Google OIDC + 서버 세션 (JWT 아님) (2026-10-12)

- **상황:** 글쓰기와 일정 관리는 소유자 1명만
- **선택지:** 아이디·비밀번호 직접 구현 / JWT / Google OIDC + 세션
- **결정:** Spring Security `oauth2Login` + Google OIDC, 서버 세션(JSESSIONID), `OWNER_EMAIL`과 일치하고 `email_verified`인 계정만 로그인 허용
- **이유:** 비밀번호를 저장하지 않음, 사용자 1명이라 서버 세션이 단순하고 즉시 로그아웃 가능(JWT는 만료 전 무효화가 어려움)
- **같이 한 것:** CSRF `csrf.spa()`(쿠키 값을 헤더로 보내는 방식), 방문자에게 세션 쿠키를 만들지 않도록 `NullRequestCache`, `/api` 비로그인은 401

## 6. 이미지 저장소: SeaweedFS (MinIO 제외) (2026-10-12)

- **상황:** S3 호환 저장소를 서버 안에 두고 싶었음(비용, 외부 비공개)
- **결정:** SeaweedFS + AWS SDK for Java v2
- **이유:** MinIO 커뮤니티판 저장소가 아카이브되어 제외. S3 API를 쓰므로 나중에 AWS S3로 바꿀 때 주소·키만 변경
- **보안:** 저장소는 외부 비공개, 이미지는 백엔드를 거쳐 업로드·제공(파일 서명으로 형식 판별, 10MB 제한)

## 7. 스키마 관리: Flyway + `ddl-auto: validate` (2026-10-12)

- **이유:** DB 구조 변경을 버전 파일로 기록, 적용된 파일은 수정 금지. Hibernate는 구조를 만들지 않고 검증만 해서 엔티티와 DB 불일치를 시작 시점에 발견

## 8. 프론트 라우팅: React Router 8 Framework 모드 + SPA (2026-10-12)

- **이유:** 라우트 모듈의 `clientLoader`로 화면 데이터 조회, 경로·파라미터 타입 자동 생성(`href()`로 링크 타입 검사), 서버 렌더링 없이 정적 파일로 배포 가능(Caddy가 제공)

## 9. 일정 입력 화면: 일정 앱 조사 후 재구성 (2026-10-13, 같은 날 10번으로 대체)

- **상황:** 처음 만든 입력 칸(제목 · 시각 · 요일 칩 7개 · 시작일 · 끝나는 날을 나열)을 소유자가 거절
- **조사:** Todoist Quick Add(제목에 "every weekday at 20:00"처럼 적으면 알아듣고 강조), Things(날짜를 말로 입력), Apple 미리 알림(반복은 매일 · 평일 · 주말 묶음 먼저, 사용자 지정에서 요일), Streaks(요일 / 주 N회 선택)
- **공통점:** 자주 쓰는 값은 기본값과 묶음으로 한 번에, 드문 설정은 접어 둠(점진적 공개), 입력과 동시에 결과를 보여 줌
- **결정:** 큰 제목 한 줄 + 한국어 해석기("토익 월수금 오후 6시 30분" → MON·WED·FRI, 18:30) + 알아들은 말 밑줄 + 한 문장 요약 + `DAILY | WEEKDAYS | WEEKENDS | CUSTOM` + 기간은 접기 + Enter 저장
- **구현 포인트:** 해석기는 앞뒤가 글자가 아닐 때만 인정해 "수학" 속 "수"를 요일로 오인하지 않음(유니코드 속성 `\p{L}` 전후 확인), 같은 종류가 여러 번이면 마지막 말을 따름, 직접 고른 값이 해석 값보다 우선. 12개 입력 예시로 확인

## 10. 일정 관리 → 글 스트릭(Streak)으로 방향 전환 (2026-10-13)

- **상황:** 입력 화면을 다시 만들었지만, 소유자가 "일정을 만든다"는 개념 자체가 맞지 않는다고 판단. 이 서비스의 핵심 행동은 공부하고 글을 쓰는 것
- **결정:** 반복 일정 등록 · 완료 체크 화면을 삭제하고, 큰 주제마다 한 달 달력에 글 쓴 날을 하위 주제 색으로 칠하는 Streak 화면으로 교체. 주제를 만들면 달력이 저절로 생기고, 글을 쓰는 것만으로 기록됨(따로 체크할 필요 없음)
- **세부:** 색 범례(그래프 범례와 같은 방식), 칸을 가리키면 그날 글 팁, 팁 제목을 누르면 공유 요소 전환으로 글 화면 제목 자리로 이동, 한 달씩 이동
- **배운 점:** 화면을 다듬기 전에 그 기능이 사용자의 실제 행동(글쓰기)과 맞는지가 먼저. 같은 데이터(글)에서 기록을 자동으로 만들면 입력 부담이 사라짐
- **남긴 것:** 일정 백엔드(API · 테이블)는 2차 Gmail 알림 설계 때 재사용 또는 삭제를 결정하려고 남김
- **이후 변경(2026-10-16):** 달력의 글 쓴 날을 만든 날이 아니라 처음 내용을 채운 날(`published_at`)로 바꿈, 목차용 `작성 예정` 글은 찍지 않음(#20)

## 11. 팝오버와 움직임 체계: Apple HIG 기준으로 정리 (2026-10-13)

- **상황:** Streak 칸을 가리키면 뜨던 팁이 세로로 길고 스크롤이 불편하다는 소유자 피드백, "부드럽게 잇는 움직임이 화면마다 통일돼 있는지" 점검 요청
- **조사 (Apple Human Interface Guidelines):** Popovers — 작은 양의 정보만, 화살표가 띄운 요소를 가리키고 그 요소를 가리지 않음, 한 번에 하나, 한 번의 클릭으로 다른 팝오버로 바꿈, 너무 크게 만들지 않음, 크기가 바뀌면 부드럽게 전환해 새 팝오버로 바뀐 것처럼 보이지 않게. Motion — 목적 있는 움직임만, 자주 하는 동작의 움직임은 짧게, 앱 전체에서 일관되게
- **팝오버 결정:** 화살표 + 칸 아래 배치, 칸 사이 이동 시 같은 팝오버가 미끄러짐, 4편까지 보이고 `+N`으로 같은 자리에서 높이 확장, 바깥 누름·Esc 닫기
- **움직임 점검 결과:** CSS에 시간 13종(0.15~1.3초), 곡선 5종이 섞여 있었음 → 용도별 토큰 5개(`--dur-quick` 0.2 / `--dur-fade` 0.3 / `--dur-ui` 0.45 / `--dur-travel` 0.8 / `--dur-move` 1초)와 곡선 3개로 통일, JS 상수도 토큰과 맞춤(그래프 확대 1.1 → 1초, 프리로더 걷힘 0.35 → 0.3초). 첫 등장 연출만 예외
- **배운 점:** 디자인 토큰을 색뿐 아니라 시간·곡선에도 두면 화면을 늘려도 움직임이 같은 언어로 유지됨

## 12. 주제 화면: 글 목록 대신 단계별 바둑판 (2026-10-13)

- **상황:** 큰 주제 메뉴를 누르면 그 아래 모든 글이 한 목록으로 쏟아져 구조가 보이지 않음 (소유자: "절대 그렇게 하지 마")
- **결정:** 단계가 깊어질수록 판이 잘게 나뉘는 바둑판. 큰 주제 → 하위 주제 2칸, 하위 주제 → 그 아래 주제 4칸, 세부 주제 → 글 8칸. 러스트 · 진한 러스트를 번갈아 칠하고 칸 사이는 세이지 선, 빈자리는 색만 칠해 판 모양 유지
- **같이 바꾼 규칙:** 글은 하위 주제(2단계 이상)에만 쓸 수 있음(서버 400 + 편집기에서 SUB 필수). 큰 주제 화면에 글이 섞이지 않도록
- **전환:** 누른 칸 이름이 다음 화면 제목으로 이어지고(주제 id별 전환 이름이라 한 화면에서 겹치지 않고 뒤로 가기도 자연스러움), 판은 서서히 흐려지며 다음 판으로. 새 칸은 제목이 자리 잡은 뒤 떠오름
- **접근성:** 러스트 위 차콜은 3.19:1이라 큰 글자 기준(굵게 18.66px 이상)만 충족 → 칸 안 글을 모두 굵게 20px 이상으로, 작은 날짜는 카드에서 뺌
- **트러블슈팅:** 처음에 "누른 칸"과 "화면 제목"에 같은 전환 이름을 쓰니 떠나는 화면에 이름이 두 개 생겨 브라우저가 전환을 건너뜀(`Unexpected duplicate view-transition-name`). React Router의 `useViewTransitionState`는 출발·도착 주소 모두에서 true라 조건부 이름으로는 막을 수 없었음 → 주제 id별 이름으로 바꿔 구조적으로 해결

## 13. 그래프 → 카드 판 전환: 별이 모여 칸이 됨 (2026-10-13)

- **요청:** 홈 그래프에서 Card를 누르면 별들이 모여서 카드로 바뀌는 느낌, Card 글자가 Category 제목으로 이어지는 느낌
- **구현:** 두 단계로 나눔. 1) 화면 안 연출: 별마다 큰 주제 별까지의 거리를 CSS 변수로 주고 `translate`로 모음(SVG의 `transform` 속성과 따로 합쳐짐), 큰 주제 별 자리에 칸 색 표지(HTML)가 커짐. 2) View Transition: 표지와 다음 화면의 칸에 같은 이름(`tile-<id>`)을 줘 브라우저가 위치·크기를 이어 줌. SVG 안의 요소에는 전환 이름을 줄 수 없어 HTML 표지를 겹쳐 쓴 것이 핵심
- **같이 고친 것:** 화면 전환마다 머리글이 새 화면과 함께 살짝 떠올라 겹쳐 보이던 문제 → 머리글에 고정 전환 이름

## 14. 연결 없는 이미지 정리: 1일 유예 후 매일 삭제 (2026-10-13)

- **상황:** 이미지는 글 저장 전(작성 중)에 먼저 올라가므로, 게시하지 않고 나가거나 본문에서 지우거나 글을 삭제하면 글과 연결 없는 이미지 기록·저장소 파일이 계속 쌓임
- **선택지:** 연결이 풀리는 순간 바로 삭제 / 주기 작업으로 유예 기간 뒤 삭제 / 정리하지 않음
- **결정:** Spring `@Scheduled`로 매일 04:00(한국 시각, 03:00 백업 뒤) 연결 없이 1일 이상 그대로인 이미지를 저장소 파일 → DB 기록 순으로 삭제
- **이유:**
  - 바로 삭제하면 작성 중(아직 저장 전)이거나 방금 지운 이미지 주소를 되돌려 넣는 경우 이미지가 깨짐
  - 유예는 처음 7일로 잡았다가 1일로 줄임: 1인 작성이라 하루 넘게 열어 둔 편집기는 드물고, 저장소를 빨리 비우는 쪽을 택함
  - 연결 해제도 `updatedAt`을 갱신하므로 해제 시점부터 기간을 셈 (별도 컬럼 불필요)
  - 파일을 먼저 지우면 도중 실패 시 기록이 남아 다음 실행에서 다시 시도. S3 DeleteObject는 없는 파일에도 성공이라 재시도해도 안전
  - backend는 파드 1개(`Recreate`)라 분산 잠금(ShedLock 등) 불필요
- **한계:** 파드를 여러 개로 늘리면 중복 실행 방지가 필요. DB 기록 없이 저장소에만 남은 파일(업로드 중 DB 저장 실패)은 대상 밖

## 18. 한 이미지를 여러 글이 함께 쓰기: 글-이미지 연결 테이블 (2026-10-14)

- **상황:** 리팩토링 중 발견. 이미지 기록(`post_image`)에 글 번호 칸이 하나뿐이라, 글 A의 이미지 주소를 글 B에 붙이면 연결이 B로 옮겨 감. B에서 그 이미지를 빼면 연결 없는 이미지가 되어 하루 뒤 정리 작업이 파일을 지우고, A에서는 이미지가 깨짐(데이터 손실)
- **선택지:** 다른 글에 이미 연결된 이미지는 옮기지 않음(첫 글만 기억) / 정리할 때 모든 글 본문을 검색 / 다대다 연결 테이블
- **결정:** 연결 테이블 `post_image_link(post_id, post_image_id)` + 연결이 모두 끊긴 시각 `unused_since`. 정리 작업은 `unused_since`가 1일 지난 이미지만 지움
- **이유:**
  - 첫 글만 기억하면 그 글에서 빼는 순간 같은 문제가 다시 생김
  - 본문 검색은 글이 늘수록 느려지고, 연결 관계를 DB 제약(FK)으로 지킬 수 없음
  - 유예 기간 기준을 `updatedAt`(아무 변경이나 갱신)에서 "마지막 연결이 끊긴 시각"으로 바꿔 뜻이 분명해짐
- **결과:** Flyway V6에서 기존 연결을 옮기고, 기존 글 본문을 정규식으로 다시 읽어 그동안 옮겨 가며 끊긴 연결도 복구. 두 글이 함께 쓰다 한 글에서 빼도 연결이 남는 테스트 추가

## 19. 기사 메일 재발송과 중복 스크랩 방지 (2026-10-14)

- **상황:** 06:00에 서버가 배포·재시작 중이거나 메일 발송이 실패하면 그날 기사 메일이 오지 않음. 같은 기사 링크로 두 번 게시하면 글이 두 개 생김
- **결정 (소유자):** 재발송은 기사 메일만(공부 알림은 제외). 같은 기사는 한 번만 스크랩
- **방법:**
  - 보낸 날을 `news_digest_log(sent_on UNIQUE)`에 기록. 06:00부터 23:00까지 매시 정각과 서버 시작 때 "06:00이 지났고 오늘 기록이 없으면" 보내고, 성공했을 때만 기록 → 꺼져 있던 날은 켜지자마자, 실패한 날은 다음 정각에 다시 시도, 이미 보낸 날은 배포로 재시작해도 다시 안 보냄
  - 06:00 기준은 따로 설정하지 않고 cron 식(`CronExpression`)에서 그날 첫 실행 시각을 계산해 설정이 한 곳에만 있음
  - 스크랩한 기사 주소를 `news_clip(url UNIQUE)`에 기록: 서버는 409로 막고, 코멘트 화면은 열 때 미리 확인해 "이미 스크랩한 기사예요" + 그 글 링크. 글을 지우면 DB가 기록도 지워(ON DELETE CASCADE) 다시 스크랩 가능
- **한계:** 지난 날짜는 재발송하지 않음(지난 아침 기사는 의미가 적음). 백엔드 파드가 여러 개가 되면 동시에 보낼 수 있어 분산 잠금(ShedLock 등) 필요. 같은 기사라도 주소가 다르면(추적용 파라미터 등) 다른 기사로 봄

## 20. 글을 쓴 날 = 처음 내용을 채운 날 (published_at, 2026-10-16)

- **상황:** AWS-SAA 목차대로 글 27개를 미리 만들어 두고(본문 `작성 예정`) 공부한 날 내용을 채움. 16일에 IAM 글을 채웠는데 Streak에는 글을 만든 12일로 찍혔고, 아직 안 쓴 26개도 12일에 몰려 찍힘
- **선택지:** 만든 시각(`created_at`)을 고쳐 쓰기 / 마지막 수정 시각(`updated_at`) 사용 / 쓴 시각을 따로 기록
- **결정:** `post.published_at`을 새로 둠(V9). `작성 예정` 글은 비어 있고, 처음 내용을 채워 저장하는 순간 그 시각이 들어가며 이후 수정으로는 바뀌지 않음. Streak·글 날짜·최신순 정렬이 이 값을 씀
- **이유:**
  - 만든 시각은 감사(audit) 기록이라 고쳐 쓰면 사실과 달라짐
  - 마지막 수정 시각은 오타 하나만 고쳐도 날짜가 옮겨 가 Streak이 흔들림
  - "목차 글"과 "실제로 쓴 글"을 구분하는 것은 이 블로그의 쓰는 방식 그 자체라 별도 값이 맞음
- **결과:** V9에서 기존 글을 옮기면서, 12일에 만든 AWS-SAA 글 중 이미 채운 글은 마지막 수정 시각을 쓴 날로 보정 → 운영에서 IAM이 16일로 찍히고 아직 안 쓴 26개는 Streak에서 빠짐(운영 Streak 화면에서 확인)
- **한계:** 내용을 다시 `작성 예정`으로 되돌려도 쓴 날은 남음(의도). 정렬은 `coalesce(published_at, created_at)`라 인덱스를 못 타지만 지금 글 수에서는 영향 없음

## 21. 글쓰기 방식: 노션식 바로 보기 편집기 대신 마크다운 원문 유지 (2026-10-17)

## 22. 그래프 큰 주제 자리: 서로 밀어내는 배치 대신 2×2 사분면 (2026-10-19)

- **상황:** OPIc 글 41개를 미리 만들자 홈 그래프가 복잡해짐. 큰 주제 별자리끼리 서로 밀어내며 자리를 정해서 어느 별자리가 어디 있는지 매번 찾아야 했고, 좁은 화면에서는 Cloud Engineer와 OPIc 별자리가 겹침
- **선택지:** 그래프 왼쪽 위에 큰 주제 탭(누르면 그 별자리로 확대) / 별자리 자리를 고정 / 둘 다
- **결정 (소유자):** 자리 고정만. 주제 id 순으로 왼쪽 위 Cloud Engineer · 오른쪽 위 SW Engineer · 왼쪽 아래 OPIc · 오른쪽 아래 News Clipping. 휴대폰(지도 폭 480px 미만)만 같은 순서 1열
- **이유:** 탭을 먼저 만들어 배포해 봤으나 머리글 주제 메뉴와 같은 목록을 한 번 더 보여 주는 느낌이 강해 뺌. 읽기 어려웠던 근본 원인은 자리가 매번 정해지는 것이라, 자리를 고정하면 탭 없이도 위치를 외울 수 있음

- **결과:** 넓은 화면·노트북 반 창·휴대폰 폭에서 Playwright로 큰 주제 별 좌표를 재어 사분면 순서와 별자리끼리 겹치지 않음을 확인
- **한계:** 큰 주제끼리 크기 차이가 크면(SW Engineer는 아직 별 하나) 작은 별자리 칸이 비어 보임. 1열로 바꾸는 기준(480px)은 화면 폭이 아니라 지도 폭
